# catalog

**Background.** Deciding which biological therapy is worth using against a given protein target means reading the trial literature pair by pair. There is no compact, machine-readable record of which binder has been shown to help patients when directed at which target.

**Contents.** One file, `graph.json`. Each entry pairs a **binder** — an antibody, peptide or other protein therapeutic, identified by its sequence rather than by a name — with the single **protein target** it is directed against, and lists the PubMed identifier of a paper reporting utility for that specific pairing. Entries are separated by study type: those reporting **clinical benefit in humans** and those reporting **preclinical** utility, which are kept in different sections and never pooled. The catalogue currently holds 55 clinical pairs across 41 targets, each resting on a single reference, and no preclinical entries yet.

**How a row is identified.** There are no drug names in the file. A binder is identified by its sequence, written one of two ways: 48 of the 55 as plain amino-acid letters (`aa:`), with `/` separating the chains where the molecule has more than one (33 of the 48 do; the other 15 are single-chain); the other 7 in HELM notation (`helm:`), which those molecules need because they carry non-standard residues — D-amino acids, acetyl or amide caps — or an explicit disulfide pattern that plain letters cannot write. A target is a UniProt accession (`uniprot:`); a citation is a bare PubMed identifier (`pmid:`). Drug names move: the same molecule carries a code name, an international non-proprietary name and a different trade name in each market, and names are reassigned, while the sequence is the molecule and does not change. The cost of that choice is real and worth stating plainly: you cannot look up trastuzumab here by name. You need the sequence, or a tool that maps a name to one.

**Inclusion.** A paper is listed only if it reports a benefit for that binder against that target — in the clinical section, benefit to patients; in the preclinical section, utility in a non-human or laboratory system. Null results and harm-only results are excluded, a paper whose study type cannot be determined is excluded, and a pair with no qualifying paper is not recorded at all. Inclusion is judged by reading the paper; no automated rule can stand in for that.

**What it is not.** Not a formulary, not dosing or prescribing guidance, and not a recommendation. It records no regulatory or approval status, no evidence grade, and no ranking — a binder's sequence and its citations are the entire record. Anything comparative is computed when the file is read, never stored in it.

**Limitations.** Protein binders and protein targets only; small molecules and nucleic acids are out of scope by design. Every pair currently rests on exactly one citation — minimum, median and maximum are all one — so citation count is not yet a measure of weight of evidence. The clinical and preclinical split records what kind of study a paper was, not how strong it was. Absence of a pair means no qualifying paper has been entered, which is not evidence that none exists.

**Skills.** [skills/resolve-key.md](./skills/resolve-key.md) goes the other way: from a stored key back to names, labels and linked records, by exact lookup rather than search. Read-only. [skills/propose-pairs.md](./skills/propose-pairs.md) is the intake procedure for adding entries — it enumerates structured sequence and activity databases rather than searching the open web, and it writes candidates to a separate proposals file. Nothing enters `graph.json` until someone has read the paper. The 55 rows now in the file predate any record of who read what; no reader or date is stored, so the repository cannot show that for any existing row.

**One skill is classed apart, and the split is the point.** The two procedures above are conservative: they only relocate facts that already exist somewhere, and the worst either can do is produce a wrong row. [skills/design-binder.md](./skills/design-binder.md) originates sequences no source has reported, where the worst failure is someone treating a hypothesis as a therapy, so it is marked `special` and serves no file here. Given a native human protein target and an indication, it first asks the catalogue, and designs a synthetic binder only where no evidenced one exists for that target in that indication; it screens candidates, orders the survivors by a named and stated scorer, and writes nothing. A designed molecule has no paper, and the file records papers, so a design is a hypothesis — it enters the catalogue only the ordinary way, when someone runs the experiment, someone publishes it, and a reader admits the row.

**Systems.** [systems/use-bench.md](./systems/use-bench.md) specifies `BENCH`, a scratchpad rather than a record: a run-scoped, append-only store where several agents working on one problem can read and write partial work at the same time without a coordinator. It is deliberately not a catalogue — every entry declares what kind of evidence it is, nothing in it is pooled across those kinds, and nothing in it reaches `graph.json`, which still admits a pair only when someone has read a paper. It is discarded when the run ends. [tracer/record-fleet-traces.md](./tracer/record-fleet-traces.md) specifies `TRACES`, the act log of one fleet run: which catalogue commit was pinned, which procedure ran, which gate refused, which triple was proposed, and a halt that can record only that the run did not read the papers. It stores no study type and no utility score, it is not a bench and not a proposal file, and it is discarded when the run ends. [`fleet/fleet.py`](./fleet/fleet.py) is the standard-library harness that emits both stores outside the repository; [`verifier/verify.py`](./verifier/verify.py) decides the trace judgements from those bytes. `fleet.campaign` is that one run. `agent.swarm` is not a spec here; the ordinary senses of the two words are pinned in [follow-agent-contract.md](./follow-agent-contract.md) §11.

**Checks.** [verifier/](./verifier/) holds `verify.py`, a standard-library-only checker for `graph.json`, and its test suite. It implements the pure predicates of [follow-agent-contract.md](./follow-agent-contract.md) §8, the relational add-only check against a predecessor file, the trace judgements in [tracer/record-fleet-traces.md](./tracer/record-fleet-traces.md) (`--trace`), and five repository extension predicates — E1, the documentation banner on every Markdown file; E2, the bijection between `skills/*.md` and follow-agent-contract.md §10; E3, a non-blocking resolution of every `pmid:` against NCBI E-utilities; E4, the bijection between `systems/*.md`, `tracer/*.md`, and follow-agent-contract.md §11; and E5, the identity line in follow-agent-contract.md §0c. GitHub Actions runs the verifier and fleet suites through `.github/workflows/validate.yml` on every push that touches `graph.json`, the verifier, the fleet harness, a skill, a system, or any Markdown file — the trigger filter is deliberately kept as wide as what the checks read, so a documentation-only change cannot slip past E1. A green run proves the pure conditions and the gating extension predicates E1, E2, E4, and E5, and nothing else: E3 runs in a separate non-blocking job, so a green run says nothing about whether the pmids resolved, and §8.16 — that a paper actually reports the benefit the row claims — is an oracle, never discharged by a machine (follow-agent-contract.md §9.6).

**Specification.** [follow-agent-contract.md](./follow-agent-contract.md) is the normative contract — schema, key grammar, inclusion rules, serialisation, merge laws and validation predicates. [pin-references.md](./pin-references.md) is a separate, pinned reference table for the external literature this repository's own methods rest on — it is **not** the catalogue's citations. Each row pins a versioned id, a retrieval date and either a byte hash or a text-layer hash with the exact extraction command, records the refereed status it could establish and says "unestablished" where it could not, and states what the paper actually measured. Its own status section is explicit that the rows were resolved by automated retrieval and that, with one noted exception, no human has read them for this repository: resolving a citation is not the oracle step `graph.json` entries require.
